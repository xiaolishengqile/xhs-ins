# 浏览器运行环境熔断设计

## 背景

采集任务依赖本机浏览器。服务从受限的桌面开发环境启动时，macOS 会在浏览器注册图形进程阶段终止 Chrome 或 Edge。当前系统只收到浏览器启动异常，并把它当成单个账号的采集失败；批量队列因此会继续启动后续账号，造成大量相同失败。

这不是账号、帖子或网络问题，而是浏览器运行环境不可用。任务级重试和平台限流都不适合处理它。

## 目标

- 第一次浏览器启动失败后，立即停止同平台后续任务，避免批量连锁失败。
- 区分“需要登录”和“浏览器运行环境不可用”，不再显示错误操作按钮。
- 用户修复运行环境后，可一次恢复同平台全部受阻任务。
- 服务重启后自动重新检测浏览器；正确启动时无需逐个重试任务。
- 保持已有平台冷却、单平台并发、部分结果保存和图片质量流程不变。

## 方案比较

### 方案一：继续按任务失败并增加重试

改动最小，但全局故障仍会被重复执行。重试会增加浏览器崩溃次数，不能解决根因，不采用。

### 方案二：浏览器管理器自行缓存失败

后续调用可以快速失败，但任务管理器仍会把每个账号写成失败；缓存何时清除也缺少清晰的用户动作，不采用。

### 方案三：错误分类加平台级熔断（采用）

浏览器层只负责给出可识别的启动错误，任务层负责把同平台队列切换为受阻状态，应用层负责显式恢复。这与现有登录阻塞、平台冷却的职责边界一致，改动集中且可测试。

## 架构

### 浏览器层

新增 `BrowserLaunchError`。系统浏览器候选全部启动失败时，浏览器管理器抛出该错误，并保留每次候选启动的简短诊断信息。采集器无需感知该错误。

### 任务层

新增任务状态 `blocked`，只表示运行环境故障，不表示账号采集失败。原有平台阻塞集合改为带原因的映射：

- `login`：任务进入 `waiting_user`，保留“打开登录窗口”和“我已处理，继续”。
- `browser`：任务进入 `blocked`，只提供“重新检测并继续”。

任务管理器捕获 `BROWSER_LAUNCH_FAILED` 后：

1. 将当前任务设为 `blocked`。
2. 立即将同平台排队任务设为 `blocked`。
3. 中止同平台正在运行的其他任务，并将其设为 `blocked`。
4. 其他平台继续运行。

启动新任务时，如果对应平台已经熔断，该任务直接进入相同受阻状态，不再尝试浏览器。

### 恢复流程

新增平台运行环境恢复操作。用户点击任一受阻任务的“重新检测并继续”后：

1. 关闭应用持有的旧浏览器上下文。
2. 清除该平台的浏览器熔断。
3. 将该平台全部 `blocked` 任务重新排队。
4. 第一个任务重新启动浏览器；成功则队列继续，失败则再次一次性熔断。

服务启动时，磁盘中的 `blocked` 任务转为排队状态，自动完成同样的重新检测。

### 接口与界面

- 控制状态保留 `blockedPlatforms` 兼容字段，并新增带 `reason`、`message` 的 `platformBlocks`。
- 任务新增 `blockReason`，取值为 `login`、`browser` 或空值。
- 新增任务恢复接口；登录接口只接受登录阻塞任务。
- 调度状态栏优先显示“浏览器运行环境受阻”，任务卡片不再为浏览器故障显示登录按钮。

## 数据兼容

现有任务没有 `blockReason` 时按空值处理。原有 `waiting_user` 任务在启动恢复时按登录阻塞兼容。新增字段继续由现有任务文件原子保存，不需要迁移脚本。

## 测试

- 浏览器候选全部失败时抛出可识别错误并保留候选诊断。
- 一个任务遇到浏览器错误后，同平台任务只发生一次浏览器尝试并统一受阻，其他平台继续。
- 新任务在平台熔断期间不启动采集。
- 恢复操作重新排队全部受阻任务；再次失败仍只熔断一次。
- 服务重启自动恢复受阻任务。
- 网页只为登录阻塞显示登录按钮，只为浏览器阻塞显示恢复按钮。
- 全量单元、集成和端到端测试保持通过。

## 非目标

- 不尝试绕过 macOS 的进程安全限制。
- 不增加浏览器守护进程、消息队列或新依赖。
- 不改变 Instagram 和小红书的页面解析、限流与图片下载策略。
